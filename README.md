# Планиметрика — MVP

Учебная платформа по планиметрии для подготовки к ЕГЭ: карточки с теорией и задачами,
роли ученик / репетитор / родитель, домашние задания и контрольные, журнал занятий,
разбор ошибок, развёрнутые (проверяемые учителем) решения. Плюс отдельный контур для
самостоятельных пользователей (без репетитора) с тарифами Free/Pro и маскотом «Гео».

## Что внутри

- **Next.js 14** (App Router, TypeScript) — фронтенд и бэкенд в одном проекте.
- **Хранилище данных — PostgreSQL** через **Drizzle ORM** (`lib/db/schema.ts`,
  `lib/db/client.ts`). Раньше был JSON-файл — мигрировали на настоящую БД с
  foreign key и транзакциями (см. раздел «База данных» ниже). Слой запросов
  изолирован в `lib/queries.ts` — компоненты и страницы никогда не обращаются
  к Drizzle напрямую.
- **API для будущего мобильного приложения** — `app/api/*` (см. одноимённый
  раздел ниже): та же бизнес-логика, что и у веба, просто по HTTP/JSON вместо
  Server Actions, с токен-авторизацией вместо cookie.
- **Роли**: STUDENT, TEACHER, PARENT — отдельные аккаунты, доступ проверяется в `middleware.ts`.
- **Иерархия программы**: Модуль (Топик, «Планиметрия») → Глава («Треугольники»,
  «Прямоугольник и квадрат», …) → Навык-урок («Теорема Пифагора», «Углы, внешний
  угол и неравенство треугольника», …). Навык — минимальная единица: у него своя
  теория и свои задачи.
- **Контент**: 6 глав, 29 навыков, 160 задач (134 с автопроверкой + 26 с развёрнутым
  решением). «Треугольники» — 7 навыков (углы, биссектрисы/медианы/высоты, все
  формулы площади включая Герона, равенство и подобие, Пифагор, Фалес/синус/косинус,
  продвинутые Чева/Менелай/Стюарт). «Прямоугольник и квадрат», «Параллелограмм и
  ромб» — по 3 навыка. «Трапеция» — 4 навыка (включая продвинутые свойства: описанная
  трапеция, отрезок между серединами диагоналей, проекция боковой стороны,
  «замечательное свойство»). «Окружность» — 8 навыков (длина/площадь, углы,
  касательные, хорды и секущие, центр вписанной/описанной окружности, вневписанная
  окружность, вписанный/описанный четырёхугольник, сектор и подобие). Новая глава
  «Четырёхугольники» — 4 навыка (общая площадь и формула Брахмагупты, теорема
  Птолемея, теорема Вариньона, дельтоид).
- **Core vs bank**: у каждой задачи есть `tier` — `"core"` (входит в обычный урок,
  чтобы урок оставался компактным) или `"bank"` (есть в общем банке навыка —
  доступна учителю для домашки/контрольной через конструктор задания, но не
  показывается в самом уроке по умолчанию). Так на каждое свойство/теорему
  приходится 3-5 задач в банке, а в дереве навыков ученик видит меньше.

  (точки касания, углы, середины медиан, точки на окружности) проверяются
  программно формулами расстояний, а не на глаз — `node scripts/dev/geometry-audit.js`.
  Стоит гонять этот скрипт при добавлении новых диаграмм с "зашитыми" координатами.

## База данных

PostgreSQL через **Drizzle ORM** (не Prisma — Prisma требует скачивания
бинарников с внешнего домена, что не везде доступно; Drizzle — чистый
TypeScript, без этой проблемы).

- `lib/db/schema.ts` — вся схема, 12 таблиц, с настоящими foreign key
  (например, `attempts.problemId → problems.id`, `ON DELETE CASCADE`) и
  Postgres enum'ами (`role`, `plan`, `answer_type`, `review_status`, ...) —
  того и другого не было в JSON-версии.
- `lib/db/client.ts` — подключение (пул соединений, кэшируется через
  `globalThis` при hot-reload в dev).
- Миграции — `drizzle-kit`: `npx drizzle-kit generate` (сгенерировать SQL из
  схемы) → `npx drizzle-kit migrate` (применить). Уже сгенерированная
  миграция лежит в `drizzle/`.
- `lib/queries.ts` — **все** обращения к БД идут только отсюда (компоненты и
  страницы никогда не импортируют `lib/db/client` напрямую). Все функции
  асинхронные.
- Множественные связанные записи (например, попытка + уведомление, или
  создание своей задачи + домашки одним действием) оборачиваются в
  `db.transaction(async (tx) => {...})` — либо всё применяется, либо ничего,
  в отличие от JSON-версии, где параллельная запись могла в теории повредить
  файл.

## API (для будущего мобильного приложения)

Веб работает через Server Actions (`app/actions.ts`) — это удобно, но
специфично для Next.js: мобильное приложение (React Native/Capacitor) так
вызывать сервер не умеет, ему нужен обычный HTTP/JSON API.

- `app/api/auth/login`, `app/api/auth/register` — вход/регистрация, в ответ
  JWT-токен (не cookie) — тот же формат токена, что и у веба, просто
  доставляется в теле ответа, а не в `Set-Cookie`.
- `app/api/dashboard` — главный экран ученика: прогресс, xp, streak, состояния
  пути обучения, энергия. Требует `Authorization: Bearer <token>`.
- `app/api/attempts` (POST) — отправка ответа на задачу. Требует токен.
- `app/api/notifications`, `app/api/curriculum` — список уведомлений (токен
  обязателен) и структура программы (публично, без токена).
- `lib/api-auth.ts` — `getBearerUser(req)`, проверяет тот же JWT, что и
  cookie-сессия у веба (см. `lib/auth.ts`) — просто из заголовка
  `Authorization`, а не из cookie. Это ДОПОЛНИТЕЛЬНЫЙ путь входа, веб
  продолжает работать через cookie как раньше.
- `lib/actions-core.ts` — бизнес-логика отправки попытки вынесена сюда одним
  куском, без ничего специфичного для транспорта (никаких `redirect`/
  `revalidatePath`/`NextResponse`). И Server Action (`submitAttemptAction`),
  и API-роут (`/api/attempts`) вызывают ровно эту функцию — при добавлении
  новых полей/условий фиксить придётся один раз, не в двух местах.

Пример вызова с телефона (или любого HTTP-клиента):

```bash
curl -X POST https://ваш-домен/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"student@demo.ru","password":"demo1234"}'
# → {"token": "...", "user": {...}}

curl https://ваш-домен/api/dashboard \
  -H "Authorization: Bearer <token>"

curl -X POST https://ваш-домен/api/attempts \
  -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
  -d '{"problemId":"p_1","answer":"60","source":"lesson"}'
```

API для учителя и родителя пока не строился (см. «Известные ограничения»
ниже) — добавляется по тому же паттерну (тонкий `route.ts` поверх
существующих функций `lib/queries.ts`, а для действий с транзакциями —
общая функция в `lib/actions-core.ts`, как с попытками).

## Интервальное повторение (SRS)

Классическая система коробок Лейтнера — 5 коробок, интервал до следующего
показа растёт с каждым верным ответом подряд, любая ошибка отбрасывает
задачу обратно в 1-ю коробку:

```
Коробка:   1     2     3     4     5
Интервал:  1д    3д    7д    14д   30д
```
(`SRS_BOX_INTERVALS_DAYS` в `lib/queries.ts`)

- Отдельная таблица `srs_states` (не путать с `attempts` — тот неизменяемый
  журнал ВСЕХ попыток, а тут только ТЕКУЩЕЕ состояние повторения по каждой
  паре ученик-задача: в какой коробке и когда показать снова).
- Обновляется в `updateSrsState()` при каждой попытке с `source IN
  ('lesson','review')` — попытки из ДЗ/контрольных на график повторения не
  влияют, это отдельный, оценочный контекст. DETAILED-задачи в SRS не
  участвуют (у них свой процесс проверки, не вписывающийся в мгновенный
  верно/неверно).
- Дашборд ученика показывает баннер с числом "созревших" задач
  (`getDueReviewCount`), если оно больше нуля — ведёт на `/student/review`.
- `/student/review` — до 15 задач за сессию (`SRS_DAILY_LIMIT`), самые
  просроченные первыми, подсказки всегда доступны (это практика, не
  контрольная). `components/ReviewFlow.tsx` — как `AssignmentFlow`, но без
  таймера.
- Важный нюанс реализации: Server Action `submitAttemptAction` **не**
  вызывает `revalidatePath("/student")` для `source="review"` — иначе
  Next.js тут же перерисовывает текущую страницу свежими серверными
  данными, где только что решённая задача уже выпала из списка "due", и
  вместо подтверждения "Верно!" с последующей поздравительной модалкой
  пользователь увидел бы пустое состояние "Повторять нечего" прямо посреди
  сессии. Проверено вручную по шагам (T+200мс/T+600мс/T+1200мс после
  ответа), а не только на глаз.

## Деплой на Vercel

Проект готов к деплою как есть — никакой особой настройки под serverless не
требуется (после фикса в `lib/db/client.ts`: пул подключений теперь кэшируется
и в проде тоже, что важно для serverless — см. комментарий в файле).

**Шаг 1 — код на GitHub.** Если репозиторий ещё не создан:

```bash
git init
git add .
git commit -m "Планиметрика — первый деплой"
```

Создайте пустой репозиторий на GitHub и запушьте:

```bash
git remote add origin https://github.com/ваш-логин/ваш-репозиторий.git
git push -u origin main
```

**Шаг 2 — применить миграции к продакшен-базе.** Это делается ОДИН РАЗ, ДО
деплоя, локально с вашего компьютера (Vercel сам это не запускает):

```bash
# .env.local должен указывать на ВАШУ продакшен-базу (Neon и т.п.)
npx drizzle-kit migrate
npm run seed   # если хотите демо-данные и в проде — необязательно
```

**Шаг 3 — импорт проекта в Vercel.**
1. [vercel.com/new](https://vercel.com/new) → выберите репозиторий с GitHub.
2. Vercel автоматически определит Next.js — настройки сборки менять не нужно.
3. **Environment Variables** — добавьте те же переменные, что в `.env.local`:
   - `DATABASE_URL` — строка подключения к Neon (с `?sslmode=require`)
   - `SESSION_SECRET` — сгенерируйте НОВОЕ значение специально для прода
     (`openssl rand -base64 32`), не переиспользуйте локальное
4. Нажмите **Deploy**.

**Шаг 4 — после первого деплоя.** Откройте выданный Vercel адрес
(`https://ваш-проект.vercel.app`) — должен открыться экран входа. Если
демо-данные не заводили в шаге 2 — заведите сейчас тем же способом, указав в
`.env.local` продакшен-`DATABASE_URL`, и запустив `npm run seed` локально ещё
раз (это применяется НАПРЯМУЮ к базе, не через сам сайт — Vercel тут ни при
чём, база — общая точка, откуда бы вы к ней ни обращались).

**На будущее** — при каждом `git push` в основную ветку Vercel передеплоивает
автоматически. Если меняли `lib/db/schema.ts` — не забудьте применить новую
миграцию (`npx drizzle-kit generate && npx drizzle-kit migrate`) к продакшен-базе
ДО пуша кода, который на неё рассчитывает.

## Уведомления в Telegram

Дублирует все 5 типов уведомлений приложения (новое задание/пробник, запись
в журнале занятий, решение проверено, задача ждёт проверки, навык пройден) в
Telegram — архитектурно дёшево: все уведомления и так проходят через одну
функцию `pushNotification()` в `lib/queries.ts`, туда и подключено.

**Привязка аккаунта.** Telegram не даёт ботам писать пользователю первыми —
только пользователь может начать диалог. Поэтому: ученик жмёт «Подключить
Telegram» в профиле → получает одноразовый код → его редиректит на
`t.me/ваш_бот?start=код` → жмёт «Старт» в Telegram → бот получает код через
вебхук → аккаунты связаны. `lib/telegram.ts` — тонкий клиент Bot API без
SDK, `app/api/webhooks/telegram/route.ts` — обработчик.

**Как включить (пошагово):**

1. В Telegram напишите **@BotFather** → `/newbot` → следуйте инструкциям —
   получите токен вида `123456:ABC-DEF...` и имя бота (`@ваш_бот`).
2. Впишите в переменные окружения (локально в `.env.local`, на Vercel —
   Settings → Environment Variables):
   ```
   TELEGRAM_BOT_TOKEN="токен от BotFather"
   TELEGRAM_BOT_USERNAME="имя_бота_без_собаки"
   TELEGRAM_WEBHOOK_SECRET="любая длинная случайная строка"
   ```
3. **После деплоя**, один раз зарегистрируйте вебхук — Telegram должен знать,
   куда слать обновления:
   ```bash
   npx tsx scripts/dev/register-telegram-webhook.ts ваш-домен.vercel.app
   ```
   (без `https://` и без слэша на конце — только сам домен). Скрипт
   использует готовую функцию `setTelegramWebhook()` из `lib/telegram.ts` —
   не нужно вручную собирать curl-запрос с JSON внутри, на Windows/PowerShell
   там легко напутать с экранированием кавычек.
4. Готово — ученики смогут подключить уведомления сами, через профиль.

**Проверка после настройки** — сначала статус (покажет, зарегистрирован ли
вебхук и была ли последняя ошибка доставки от самого Telegram):
```bash
npx tsx scripts/dev/diagnose-telegram.ts
```
Затем реальная отправка:
```bash
npx tsx scripts/dev/test-telegram-send.ts <ваш_chat_id>
```
(свой `chat_id` можно узнать, написав `@userinfobot` в Telegram).

**Честно о тестировании.** Как и с ЮKassa — я не смог протестировать это
end-to-end сам: нужен реальный токен бота, которого у меня быть не может.
Но здесь ограничение оказалось даже глубже — при попытке проверить
`sendTelegramMessage` изолированно выяснилось, что моя рабочая песочница
вообще не имеет сетевого доступа к `api.telegram.org` (список разрешённых
доменов у меня ограничен). Зато это честно подтвердило важную вещь:
обработка ошибки сработала правильно — `sendTelegramMessage` вернула
`false`, ничего не упало, попытка отправки не сломала запись самого
уведомления в БД (проверено — уведомление создалось). Всю цепочку **до**
реального вызова Bot API (генерация кода, редирект на t.me-ссылку, приём
вебхука, привязка `chat_id` к пользователю, очистка одноразового кода)
проверил напрямую в базе данных — работает.

## Admin-панель и оплата через ЮKassa

**Admin-панель** (`/admin`) — доступна пользователям с `isAdmin=true` в базе
(демо: `teacher@demo.ru` — в этом продукте единственный репетитор одновременно
и владелец платформы). Проверка доступа — на уровне страниц через
`requireAdmin()` в `lib/auth.ts`, не в `middleware.ts`: `isAdmin` не закодирован
в JWT сессии, а middleware работает на Edge-рантайме без доступа к Postgres
через `pg`.

- `/admin` — список всех самостоятельных пользователей (без привязки к
  репетитору — только у них есть понятие тарифа), с ручной выдачей/отзывом Pro
  (на N дней или бессрочно) — на случай проблем с оплатой.
- `/admin/user/[id]` — детали конкретного пользователя + история его платежей.
- `/admin/payments` — все платежи по всей системе, с общей суммой успешных.

**Оплата через ЮKassa** — разовый платёж за период (по умолчанию 30 дней),
**не автосписание**: для рекуррентных платежей ЮKassa требует отдельного
согласования с их менеджером через чат в личном кабинете — это не техническое
ограничение, а бизнес-процесс на их стороне.

- `lib/yookassa.ts` — тонкий клиент REST API v3 (без SDK), создание платежа
  + проверка IP входящих вебхуков (ЮKassa рекомендует именно это, не подпись,
  в отличие от многих других платёжных систем).
- `app/actions-payments.ts` — `startPaymentAction`, создаёт платёж в ЮKassa и
  редиректит пользователя на страницу оплаты.
- `app/api/webhooks/yookassa/route.ts` — обработчик уведомлений об изменении
  статуса платежа. Жёстко отклоняет (403) запросы не из документированных
  диапазонов IP ЮKassa — иначе кто угодно мог бы прислать поддельное
  "оплата прошла" и получить Pro бесплатно.
- Продление **идемпотентно** (повторно доставленный вебхук не продлит
  подписку дважды) и **накопительно** (оплата до истечения текущего периода
  добавляет дни к остатку, а не считает от "сейчас").

**Включается только через переменные окружения** — `YOOKASSA_SHOP_ID` и
`YOOKASSA_SECRET_KEY` (см. `.env.local.example`). Если не заданы — кнопка
"Перейти на Pro" работает в прежнем демо-режиме (мгновенно, бесплатно),
ничего не ломается для тех, кто ещё не настроил оплату.

Так как я не располагаю реальными ключами ЮKassa, `lib/yookassa.ts` и сам
редирект на страницу оплаты не протестированы end-to-end — реализовано
аккуратно по документации ЮKassa, но финальная проверка на живых запросах
осталась за тем, у кого есть доступ к личному кабинету. Логика на нашей
стороне (создание pending-платежа, обработка вебхука, идемпотентность,
корректное продление) проверена отдельным скриптом, симулирующим вебхук:

```bash
npx tsx scripts/dev/test-payment-flow.ts
```

## Мультипредметность и подготовка к сторам (в процессе)

Стратегический сдвиг: платформа перестаёт быть только про планиметрию —
план включает ещё 11 разделов профильного ЕГЭ (Стереометрия, Тригонометрия,
Теория вероятности и т.д.), публикацию в App Store/Google Play через
Capacitor, и распространение нового дизайна на роли учителя и родителя.
Название решили оставить прежним — "Планиметрика" теперь бренд платформы
целиком, а не только курса геометрии (как "Skyeng" не означает "только
небо").

**Структурная основа (первый шаг) — сделана:**
- Схема БД уже поддерживала несколько предметов на уровне данных

## Производительность — устранён водопад запросов к БД

Найдена и исправлена вероятная главная причина "долгой загрузки страниц" —
**не хостинг, а сам код**. На дашборде ученика (`app/student/page.tsx`) было
**12 независимых запросов к базе, идущих строго последовательно**
(`await X; await Y; await Z...`), хотя ни один не зависел от результата
другого — все опирались только на `user.id`, известный заранее. Каждый такой
`await` — это отдельный круговой обмен пакетами до Neon через интернет; на
serverless Postgres это может быть 30-80мс на запрос. 12 запросов подряд —
до 900мс чистой сетевой задержки на одном экране, прежде чем вообще
начинается рендер.

Исправлено во всех местах, где нашёлся тот же паттерн — заменено на
`Promise.all([...])`, то есть по факту одна задержка вместо N:

- `app/student/page.tsx` — 12 запросов → 1 параллельный блок
- `components/StudentShell.tsx` (используется почти на каждой странице
  ученика) — 5 запросов → 1 параллельный блок
- `app/student/skill/[id]/page.tsx` — 4 запроса → 1 параллельный блок
- `app/student/program/page.tsx` — 2 запроса → 1 параллельный блок
- `app/teacher/student/[id]/page.tsx` — 8 запросов → 1 параллельный блок
- `app/teacher/page.tsx`, `app/parent/page.tsx` — внутри `map` по каждому
  ученику/ребёнку было 2 последовательных запроса, теперь параллельно

**Честно о проверке**: у меня в песочнице локальный Postgres на той же
машине — сетевой задержки нет вообще, поэтому эффект здесь замерить нельзя
(миллисекунды что до, что после). Сама корректность (одинаковые данные,
ничего не сломалось) проверена полной регрессией по всем ролям. Реальный
эффект будет виден именно на Neon — там каждый круговой обмен стоит
десятки миллисекунд, и именно там 12→1 даёт наибольшую разницу.

Если после этого фикса страницы всё ещё ощущаются медленными — вероятные
следующие подозреваемые: холодный старт Neon (первый запрос после простоя
базы) или холодный старт самой serverless-функции на Vercel — оба не
лечатся в коде приложения, тут уже вопрос тарифа/инфраструктуры.

## Черновик поверх диаграммы

Тап по диаграмме в карточке задачи (иконка ✏️ в углу) открывает полноэкранный
режим рисования — `components/diagrams/DiagramScratchpad.tsx`. Диаграмма
показывается крупнее как подложка, поверх неё прозрачный `<canvas>` для
пометок от руки. Инструменты: ручка, прямая линия, ластик, отмена последнего
штриха, полная очистка, 3 цвета.

**Сознательно эфемерно** — пометки не сохраняются между открытиями (ни в базу,
ни в `localStorage`), сбрасываются при закрытии. Обсуждали это явно перед тем,
как строить: сохранение потребовало бы решить формат хранения (снимок-картинка
или векторные штрихи) и добавить новую таблицу — для v1 предпочли самый
дешёвый путь, черновик и есть черновик, как бумажный.

Рисование сделано через ручное управление `<canvas>` (не библиотека) —
Pointer Events (единый обработчик для мыши/тача/пера), перерисовка всех
штрихов при каждом изменении (не инкрементальная — при таком объёме штрихов
на одну задачу разница в производительности не заметна, зато `undo` и ластик
тривиальны). Ластик — не "стирание видимости", а реальное стирание пикселей
через `globalCompositeOperation: "destination-out"`.

По пути поймал и исправил классическую для React 18 ошибку: `setStrokes`
вызывался с функцией-апдейтером, ссылавшейся на `drawing.current.points`,
а следующей строкой этот `drawing.current` обнулялся — так как апдейтер
выполняется асинхронно, к моменту вызова он читал уже пустой массив. Штрихи
существовали в состоянии (кнопки "Отменить"/"Очистить" становились активны),
но были физически невидимы. Поймал не по ощущению "не работает", а проверив
напрямую количество закрашенных пикселей через `canvas.getImageData()` — и
после фикса тем же способом подтвердил: пиксели появляются при рисовании и
пропадают при стирании/очистке.

## Мобильная версия — PWA

Приложение можно «установить» на телефон как обычное приложение — иконка на
экране, полноэкранный режим без адресной строки браузера. Это первый шаг из
трёх возможных путей к мобильной версии (PWA → Capacitor для публикации в
сторах → React Native при реальной необходимости) — начали с самого дешёвого
по трудозатратам, дальше по факту появления конкретной причины.

- `public/manifest.webmanifest` — имя, иконки, `display: "standalone"`,
  цвет темы (`#1CAE6B`, фирменный зелёный).
- `public/sw.js` — service worker с **осознанно минимальным** кэшированием:
  кэшируется только неизменяемая статика Next.js (`/_next/static/*`,
  версionируется хэшем в имени файла — один URL всегда один и тот же
  контент) и иконки. **Страницы и `/api/*` никогда не кэшируются** —
  агрессивный кэш означал бы иногда показывать устаревшую энергию/прогресс/
  уведомления, что для обучающего приложения хуже, чем отсутствие офлайн-
  режима вообще.
- `components/ServiceWorkerRegister.tsx` — регистрирует worker на клиенте,
  подключён в `app/layout.tsx`.
- Иконки в `public/icons/` сгенерированы из самого Гео (не из логотипа-буквы
  «П») — отрендерены через реальный компонент `Mascot` и заскриншочены
  Playwright'ом в нужных размерах, включая отдельную **maskable**-версию с
  увеличенным безопасным отступом (Android обрезает иконки в разные формы —
  круг, скруглённый квадрат — обычная иконка без отступа потеряла бы края).

Проверено: service worker реально регистрируется и переходит в `activated`,
манифест валиден и отдаётся, критерии установки (manifest + service worker +
HTTPS) выполнены. В кэш после навигации по приложению попадает только статика
— ни одна страница, ни один `/api/*`-запрос, проверено напрямую через
`caches.keys()`/`cache.keys()` в браузере, не на словах.

## Установка и запуск (первый раз)

**Нужен PostgreSQL** (локально или облачный — Vercel Postgres/Neon/Supabase/Railway
всё подходит, у всех есть бесплатный тир). Локально на Ubuntu/Debian:

```bash
sudo apt-get install -y postgresql postgresql-contrib
sudo service postgresql start
sudo -u postgres psql -c "CREATE USER mathapp WITH PASSWORD 'ваш_пароль' CREATEDB;"
sudo -u postgres psql -c "CREATE DATABASE mathapp OWNER mathapp;"
```

Создайте `.env.local` в корне проекта:

```
DATABASE_URL="postgresql://mathapp:ваш_пароль@localhost:5432/mathapp"
SESSION_SECRET="длинная-случайная-строка-замените-в-проде"
```

Затем:

```bash
npm install
npx drizzle-kit migrate   # создаёт таблицы по схеме lib/db/schema.ts
npm run seed               # заполняет демо-данными
npm run dev
```

Откройте **http://localhost:3000**. Для последующих запусков — `npm run dev`
(но убедитесь, что Postgres запущен: `sudo service postgresql start`).

## Как устроено обучение (для ученика)

Путь обучения — не список карточек, а **визуальная извилистая тропинка**
(`components/SkillPath.tsx`) для каждой главы: узлы-навыки соединены плавной
линией (кубические Безье через координаты, посчитанные синусоидой — не
идеальный зигзаг, органичная "тропинка", как в Duolingo). Пройденный отрезок
пути подсвечен цветом главы, оставшийся — бледный. Гео стоит прямо на текущем
узле. Позиции подписей чередуются по бокам от узла в зависимости от того, в
какую сторону узел смещён — не наезжают на соседние.

Открыв навык, ученик сначала проходит **карточки теории** (одна мысль на карточку:
Гео + заголовок, формула, объяснение, иногда — схема), затем переходит к
**задачам по одной**:

- У 51% задач (82 из 160) есть **схематичная диаграмма** (не в масштабе, как на
  реальном ЕГЭ) — 10 параметрических SVG-компонентов в `components/diagrams/`
  на основные фигуры программы. Процент снизился после добавления продвинутых
  тем (теоремы Птолемея/Вариньона, центры окружностей треугольника и т.п.) —
  для них, как и для Чевы/Менелая/Стюарта ранее, диаграмм пока нет (нет подходящих
  шаблонов, а рисовать "на глаз" не хотим — см. `scripts/dev/geometry-audit.js`
  зачем). У каждой задачи также есть **формула-подсказка**, доступная по кнопке
  в любой момент.
- При неверном ответе ответ **не раскрывается** — вместо этого показывается
  подсказка, которая усиливается с каждой попыткой (1-я — концептуальная, 2-я —
  конкретнее). С 3-й ошибки можно самостоятельно открыть разбор.
- К теории можно вернуться в любой момент кнопкой «Теория» — она откроется поверх
  текущей задачи и не собьёт прогресс.
- Есть некоторые задачи с **развёрнутым решением** (текстовое поле вместо короткого
  ответа) — они не проверяются автоматически, а уходят репетитору на ревью.
- Серия верных ответов подряд показывает **комбо-бейдж**, который остаётся в шапке
  всё время решения. Закрытие навыка празднуется конфетти и анимированным счётчиком
  XP (+10 за задачу, +30 бонусом за навык без единой ошибки).
- **Уровни/звания** (`getLevelInfo` в `lib/queries.ts`) — обёртка над XP для наглядной
  прогрессии: Новичок → Знаток фигур → Мастер линий → Гений треугольников → Виртуоз
  планиметрии → Легенда ЕГЭ. Карточка на дашборде показывает текущее звание и полосу
  прогресса до следующего.
- **Streak** в шапке растёт не только числом, но и визуально — огонёк крупнее и ярче
  при 3+/7+/14+ днях подряд (на 14+ добавляется лёгкое свечение и пульсация).
- Навыки открываются последовательно — следующий доступен только когда предыдущий
  пройден на 100% (в том числе дождался проверки, если там было развёрнутое решение).

## Домашка, контрольные и пробники

Помимо обычной домашки (с подсказками) репетитор может назначить **контрольную
работу** или **пробный экзамен** — они по умолчанию идут без подсказок и без
возможности открыть разбор (реальные условия экзамена), задачи можно брать из
любых навыков программы, а не только из одной темы.

Для любого типа задания можно задать **лимит времени** (в минутах) — на странице
задания появится обратный отсчёт, который не сбрасывается при обновлении
страницы (момент старта фиксируется на сервере). Когда время выходит, ввод новых
ответов блокируется, но уже решённые задачи и разбор остаются доступны.

## Маскот «Гео»

Официальный персонаж бренда — «математический дух», по мотивам брендбука
(изначальный референс — тьютор, сгенерировано отдельно). Гео — не картинки, а
полностью SVG-персонаж (`components/Mascot.tsx`), собранный из отдельных
анимируемых частей: тело, два глаза, рот, две руки, орбитирующие
геометрические спутники. Палитра — точные цвета брендбука (`#22C55E`,
`#6EE7B7`, `#EFFFF7`, `#0F5132`).

Что реально анимируется (не картинка целиком, а части независимо):
- **Дыхание** — тело плавно пульсирует по масштабу
- **Моргание** — глаза закрываются на случайный интервал (2.2–4.8 сек), не
  механически по таймеру, а с разбросом — выглядит органично
- **Взмах рукой / руки вверх** — зависит от настроения
- **Орбита спутников** — треугольник/круг/квадрат вращаются вокруг персонажа
- **Искры/сердечки/лампочка/zzz** — по настроению, пульсируют

10 настроений (`MascotMood` в `components/Mascot.tsx`), у каждого — своя
комбинация формы глаз/рта/рук/доп. элемента: `idle`, `happy`, `celebrating`,
`thinking` (рука у лица), `sleepy` (zzz), `worried`, `surprised` (!), `wink`,
`love` (сердечки вместо глаз), `hint` (лампочка, рука указывает).

Гео — заметная часть интерфейса ученика (не показывается в кабинете учителя и
родителя — это специально его личный спутник, а не общий брендинг):
- **Шапка** (только у роли "ученик") — заменяет логотип-плашку, кликабелен:
  тап показывает случайную поддерживающую фразу в облачке (`interactive`
  проп).
- **Дашборд** — крупная карточка сверху, настроение зависит от прогресса
  (idle → happy → celebrating при 100% модуля, worried при нулевой энергии).
- **Карточка задачи** — `thinking` рядом с подсказкой при неверном ответе,
  `love` рядом с "Верно!" при первом решении.
- **Модалка завершения темы** — `celebrating`, вместе с конфетти.
- **Вход, регистрация, страница тарифа, пустые состояния** (список пробников).

Следующий шаг по плану (см. историю разработки) — довести Гео до ещё большего
числа мест (карточки теории и т.д.) и переделать путь обучения в визуальную
тропинку/карту вместо списка карточек.

## Свои задачи учителя (без банка)

На странице создания задания (`/teacher/homework/new`) есть блок "Свои задачи

в том конкретном задании, для которого их написали. В интерфейсе ученика они
подписаны как "Своя задача" вместо названия навыка.

## Самостоятельные пользователи и тарифы Free/Pro

Помимо учеников репетитора, теперь можно **зарегистрироваться самостоятельно**
на `/register` — без привязки к учителю (`teacherId` не задан). У таких
пользователей:

- **Домашка, журнал занятий, разбор ошибок у учителя — недоступны** (это
  специфика отношений с репетитором, у самостоятельных пользователей их
  просто нет).
- **Free-план**: открыта только первая глава («Треугольники»), остальные 4 —
  под замком с апсейлом на Pro. Ограниченная энергия (по умолчанию 5,
  восстанавливается по 1 каждые 30 минут — см. `FREE_MAX_ENERGY` и
  `ENERGY_RECHARGE_MINUTES` в `lib/queries.ts`) — тратится на КАЖДУЮ НОВУЮ
  задачу (повторные попытки после подсказки бесплатны). Развёрнутые
  (DETAILED) задачи скрыты — без Pro и без учителя их некому проверять.
- **Pro-план**: все главы, безлимитная энергия, доступны развёрнутые задачи с
  мгновенной самопроверкой (эталонное решение раскрывается сразу — статус
  попытки `self_checked`, отдельно от `approved` учителем), доступны
  «авторские пробники» (`Homework.audience === "pro_standalone"` —
  не привязаны к конкретному ученику, доступны любому Pro-пользователю).
  Переключение тарифа на `/student/upgrade` — мгновенное, без реальной
  оплаты (это MVP-демонстрация концепции, не платёжный интеграция).

Ученики репетитора (с `teacherId`) полностью НЕ затронуты этой системой —
энергия у них всегда безлимитна, все главы всегда открыты, независимо от поля
`plan` (которое для них просто не используется).

## Редактирование контента через интерфейс (UI)

С этого момента редактировать главы/навыки/задачи можно **прямо в
интерфейсе**, без правки кода — `/teacher/content` (ссылка «Контент
программы» на дашборде учителя):

- **Обзор** — дерево Модуль → Глава → Навык со счётчиками (сколько карточек
  теории, сколько задач в банке), плюс «+ Добавить главу».
- **Навык** (`/teacher/content/skill/[id]`) — редактирование названия/порядка,
  **конструктор карточек теории** (добавить/убрать/переставить местами —
  `components/TheoryCardsBuilder.tsx`), и список всех задач банка с
  редактированием/удалением, плюс «+ Задача».
- **Задача** (создание/редактирование, `components/ProblemForm.tsx`) — текст,
  тип ответа, правильный ответ, подсказки (по одной на строку), разбор,
  сложность, `tier` (core — в уроке / bank — только в банке для ДЗ), и
  **диаграмма как JSON с живым превью** прямо в форме (используется тот же
  `DiagramRenderer`, что и у ученика — что видите в форме, то увидит и он).
- **Удаление задачи заблокировано**, если по ней уже есть попытки учеников
  (`countAttemptsForProblem` в `lib/queries.ts`) — иначе внешний ключ
  `attempts.problemId → problems.id` с `ON DELETE CASCADE` стёр бы их
  историю прогресса. Показывается понятное сообщение вместо тихого отказа.
- Создание новой ГЛАВЫ и нового НАВЫКА работает так же, отдельные формы.

Ограничения текущей версии UI, честно:
- Создавать/редактировать TOPIC (сам модуль «Планиметрия») нельзя — он один,
  не было причины усложнять.
- Диаграмма редактируется как сырой JSON, не визуальным конструктором —
  требует знания формата (см. пропсы конкретного компонента в
  `components/diagrams/`). Для карточек теории диаграмму пока можно задать
  только через `scripts/seed.ts` (в форме теории её нет).
- Контент общий на всё приложение (не привязан к конкретному учителю) — при
  одном репетиторе (как задумано сейчас) это не проблема, но если когда-то
  понадобится несколько независимых репетиторов на одном деплое — тут нужна
  будет доработка (привязка контента к `teacherId` или отдельные инстансы).

## Массовое наполнение через seed.ts (для больших объёмов)

Для добавления сразу МНОГИХ задач (как в этом MVP — сотни за раз) удобнее
редактировать **`scripts/seed.ts`** напрямую, чем кликать через UI по одной:

- `db.subtopics.push(...)` — главы.
- `db.skills.push(...)` — навыки, каждый со своими `theoryCards` (заголовок,
  формула, текст, опционально `diagram`).
- `db.problems.push(...)` — задачи, каждая с `diagram`, `keyFormula`, `hints[]`
  (без ответа!), `explanation`, `correctAnswer`.

Диаграммы — параметрические SVG-компоненты в `components/diagrams/`: 10 штук
(`triangleAngles`, `triangleRight`, `triangleCevian`, `triangleSimilarPair`,
`triangleSides`, `triangleExteriorAngle`, `rectangle`, `parallelogram`,
`trapezoid`, `circle`), каждый принимает подписи как пропсы. Чтобы добавить
диаграмму к задаче, укажите `diagram: { kind: "...", ...подписи }` — смотрите
примеры в `scripts/seed.ts` или пропсы конкретного компонента.

**После правки `scripts/seed.ts` просто запустите `npm run seed` — это
безопасно.** У каждой темы/навыка/задачи есть стабильный id (`t_1`, `sk_3`,
`p_12`...), который не меняется между запусками, поэтому `npm run seed`:

- **upsert'ит** (insert ... on conflict do update) тексты/подсказки/диаграммы
  у уже существующих задач и навыков прямо в Postgres;
- добавляет новые задачи/навыки/главы, если вы дописали их в файл;
- **не трогает вообще** таблицы пользователей, попыток, домашних заданий,
  журнала занятий и уведомлений — они просто остаются в базе как есть, скрипт
  их даже не читает при обычном (не `--reset`) запуске.

Важное правило для стабильности id: **новые блоки дописывайте в конец**
соответствующего раздела (конец списка задач навыка, конец списка навыков и
т.д.), а не вставляйте в середину — вставка в середину сдвинет автоматически
генерируемые id всех элементов того же типа, что идут после неё. (Задачи,
добавленные через UI, получают случайный id через `genId()` — они с этим
правилом не связаны, оно касается только seed.ts.)

Если действительно нужна абсолютно чистая база (например, для локальной
разработки) — `npm run seed:reset` работает как раньше: полностью стирает и
пересоздаёт всё, включая пользователей и демо-данные.

- Уведомления только внутри приложения — нет email/push, узнать о новом
  уведомлении можно только зайдя и посмотрев на колокольчик.
- Skill tree разбит на несколько навыков только у главы «Треугольники» —

- Нет UI для добавления/редактирования задач без правки кода — но, в отличие от

  безопасно (см. раздел выше), это уже не угроза потерять данные.

- Полного покрытия программы ЕГЭ — контент осознанно ограничен планиметрией, но

  теорему, а не по одной задаче на тему.

## Дальнейшие шаги

## Обязательная теория при первом знакомстве с темой

Раньше (после большого редизайна) теория была ВСЕГДА по кнопке, никогда не
навязана — принцип "ровно одно очевидное следующее действие". Но для
совершенно новой темы (например, ученик впервые открывает "Теория
вероятности" после привычной планиметрии) сразу бросать в задачу без
единого слова контекста оказалось слишком резко.

Компромисс: теория идёт ПЕРЕД задачами (`components/LessonFlow.tsx`,
проп `forceTheoryFirst`), но только если ученик ещё НИ РАЗУ не решал
задачи во всей ЭТОЙ ТЕМЕ целиком (не навыке — проверка через
`allSkills.some(s => progress[s.id]?.solved > 0)` по всем навыкам темы,
`app/student/skill/[id]/page.tsx`). Как только решена хотя бы одна задача
в теме — все следующие навыки (внутри той же темы) открываются сразу с
задачей, как и раньше. Если у навыка нет карточек теории вообще —
показывать нечего, сразу к задачам, даже при первом заходе.

Проверено сквозным сценарием: свежий ученик впервые заходит в тему →
видит теорию (не задачу) → проходит её → видит реальную задачу и решает
→ заходит во ВТОРОЙ навык той же темы → теория уже не навязана, сразу
задача. Заодно обновил регрессионные тесты (`test_pg_all_roles.js`,
`test_probability_answer.js`) — они теперь честно проходят через теорию
там, где она ожидаемо появляется, а не просто исторически не знали о ней.

## Четвёртый предмет: Показательные и логарифмические (6 навыков, в процессе)

**Важное уточнение от пользователя**: подборка Ященко для №13 (тригонометрия)
на самом деле смешанная — содержит и логарифмы/показательные, не только
тригонометрию. Учту при следующем чтении, буду распределять по темам, а не
считать её чисто тригонометрической. Также загружен новый архив (номер
15 — неравенства) с явным фильтром: только показательные/логарифмические
неравенства + метод интервалов, БЕЗ модулей и корней (урок 8 архива с
ними — пропущен целиком, даже не извлекал).

Собрал 6 навыков (по мере чтения материалов — оба урока про степени/
логарифмы, плюс урок 1 и урок 2 из архива про неравенства):

1. **Свойства степеней** (5 задач) — приведение к общему основанию,
   разложение на множители, замена переменной для симметричных выражений
   вида aˣ+a⁻ˣ.
2. **Логарифмы: определение и свойства** (11 задач) — от простых примеров
   на одно свойство до сложных многошаговых (например, перестановка
   оснований в степени через a^(logᵦc)=c^(logᵦa)).
3. **Показательные уравнения** (5 задач) — приведение к одному основанию,
   деление на общий множитель, квадратное уравнение в показателе степени.
4. **Логарифмические уравнения** (7 задач) — от простого `logₐf(x)=c` до
   переменного основания логарифма (`log_(x-3)4=2`, где после возведения
   в степень по определению получаются ДВА кандидата на корень, и один
   отсеивается по ОДЗ — важная, часто упускаемая техника).

Урок 2 содержал 32 задачи — отобрал ~12 самых показательных и
разнообразных по технике, а не занёс всё подряд (та же логика "не
раздувать уроки", что применил и к тригонометрии).

**По пути поймал у себя реальную ошибку распознавания PDF, не занёс бы
верный ответ к неверному условию.** При проверке задачи "2·(u²)³²·(5u)²
: u⁶⁶" через Python с одной интерпретацией формулы получил РАЗНЫЕ
значения при разных u (хотя ответ должен быть константой) — это сразу
показало, что я неверно распознал степень при чтении PDF. Перечитал
внимательнее (спутал "u²" — квадрат числа u — с частью более длинного
показателя "3/2"), пересчитал с исправленной формулой — сошлось точно
(50 при любом u). Без этой проверки в базу ушла бы задача с текстом от
одной формулы и ответом от другой. Аналогично перепроверил через Python
все ключевые значения из урока 2 (включая финальную задачу с квадратным
уравнением через сокращение общего знаменателя logₐx) перед занесением.

Заодно подтвердил, что доработка "холст без диаграммы" (см. предыдущий
раздел) автоматически работает и для нового контента — кнопка "✏️
Черновик" появилась на первой же задаче новой темы без дополнительных
действий.

5. **Метод интервалов** (4 задачи, `DETAILED`) — «хорошие»/«плохие»
   скобки, чётная/нечётная кратность корня, включая пример с двумя
   квадратными трёхчленами без корней (дискриминант<0), которые просто
   не меняют знак всего выражения.
6. **Показательные неравенства** (7 задач, `DETAILED`) — элементарные
   неравенства с переходом к сравнению аргументов (со сменой знака при
   основании 0<a<1), приведение разных оснований через логарифм, замена
   переменной с обязательным учётом ограничения t>0 при обратной замене,
   и **однородные показательные неравенства** (урок 6, номер 15) —
   деление на общий множитель, обратная замена «по кускам».
7. **Логарифмические неравенства** (7 задач, `DETAILED`) — элементарные,
   замена t=logₐx (важное отличие от показательных — здесь у t НЕТ
   ограничения на знак), вынесение чётной/нечётной степени из аргумента
   с осторожностью насчёт модуля, обратная замена «по кускам» с точечным
   решением, и **метод рационализации** — доведён от теории (была только
   формула в карточке) до двух реальных разобранных задач: простая
   `log_(x+1)(x−1)⩾0` (core) и сложная с двумя логарифмами-множителями
   `(x²+3x−10)·log₀,₅(x²−1)·log_(x²−1)(x+2)⩽0` (bank).
8. **Комбинированные показательные уравнения** (2 задачи, `DETAILED`,
   позиция 4 — между элементарными показательными и логарифмическими) —
   однородные уравнения с двумя/тремя разными основаниями (9ˣ, 6ˣ, 4ˣ,
   образующими геометрическую прогрессию), деление на общий множитель,
   замена t=(a/b)ˣ, отбор корня через сравнение с иррациональным числом
   (не приближённо в уме, а через возведение в степень).

**Порядок навыков по возрастанию сложности — проверен и подтверждён.**
Итоговая последовательность: выражения (1-2) → элементарные показательные
уравнения (3) → **комбинированные показательные уравнения (4)** →
логарифмические уравнения (5) → метод интервалов (6, как техническая
предпосылка) → показательные неравенства (7) → логарифмические
неравенства (8, финал с методом рационализации). Для тригонометрии
порядок уже был верным без изменений.

**Ещё одна пойманная ошибка распознавания PDF — тот же паттерн, что и
раньше.** При проверке однородного показательного неравенства через
Python заявленная граница ответа (x=−1) не сошлась с моей первой
интерпретацией формулы (показатель степени 2/x²). Не списал на "наверное
округление" — перепроверил с альтернативной гипотезой (показатель 2/x,
без квадрата) и обе границы (x=−1 и x=2) сошлись ТОЧНО в ноль. Значит я
неверно распознал степень при чтении PDF — квадрат в показателе там,
где его не было. Занёс задачу только с исправленной формулой.

**Осознанно не стал читать урок 7 номера 15** ("задачи прошлых лет на
все методы") и оставшуюся часть подборки Ященко для №13 — по духу это
дополнительная практика на уже изученные техники, а не новый учебный

пропущен по фильтру пользователя с самого начала).

**Пробел из прошлого раза закрыт материалом из номера 13** (не выдуман

**По пути снова напоролся на свою известную повторяющуюся ошибку** — при

- Новая кнопка "✏️ Черновик" в панели инструментов `ProblemCard` —

## Третий предмет: Тригонометрия (в процессе, большой объём)

Единая тема от простых выражений к сложным уравнениям (по договорённости —
"хороший путь от простой тригонометрии к сложной"). Источник — 9 уроков
преподавателя (~400 страниц, архивы "6-7 номер УРАВНЕНИЯ" и "13 номер") —
базовая тригонометрия (4 урока) + продвинутые методы решения уравнений
(5 уроков, номер 13 ЕГЭ) как углубление той же темы, не отдельный раздел.

Прочитано и внедрено (5 из ~7-8 планируемых навыков):
1. **Тригонометрические тождества и выражения** (18 задач) — формулы
   приведения, двойной угол, чётность/нечётность, ОТТ.
2. **Элементарные тригонометрические уравнения** (8 задач) — sin x=a,
   cos x=a, tg x=a, ctg x=a с отбором корня (наибольший отрицательный/
   наименьший положительный).
3. **Методы решения тригонометрических уравнений** (6 задач, формат
   `DETAILED` — развёрнутое решение) — разложение на множители,
   группировка, замена переменной t=sin x/cos x, отбор корней на отрезке
   двойным неравенством или через окружность.
4. **Однородные и неоднородные уравнения** (5 задач, `DETAILED`) —
   однородные 1-й и 2-й степени (с доказательством, почему cos x=0 не
   подходит), сведение неоднородных к однородным через ОТТ, метод
   вспомогательного угла для a·sinx+b·cosx=c.
5. **Задачи прошлых лет (ЕГЭ)** (7 задач, `DETAILED`) — реальные задачи
   №13 из ЕГЭ 2023-2024, включая одну с ОДЗ и показательно-тригонометрическим
   выражением (перепроверил через Python — и сам корень отбора, и
   выполнение ОДЗ sin x>0).

**Дополнительные задачи в банк (не в core-урок) — по обратной связи "не
раздувать уроки".** Прочитал урок 8 ("задачи на все методы") — 6 задач, из
них 5 чисто тригонометрических (включая 2 с логарифмом ВНУТРИ
тригонометрического уравнения — интересная комбинация техник), одна
оказалась чисто показательным уравнением без тригонометрии вообще —
отложил её для будущего раздела логарифмов, не стал искусственно
пристраивать не по теме. Все 5 добавлены с `tier: "bank"` в уже
существующие навыки (методы/однородные/задачи прошлых лет) — core-урок
не увеличился, но у учителей стало больше вариантов для ДЗ и контрольных.
Заодно по пути обнаружил, что подборка "Ященко для номеров 6-7" на самом
деле про **показательные уравнения и логарифмы**, а не тригонометрию —
заголовок был точным ("Тригонометрия И логарифмы"), просто я не сразу
понял, что темы разделены по вариантам. Отложил этот материал целиком до
раздела логарифмов, не стал использовать не по назначению.

Все ответы перепроверены численно через Python (`math.sin/cos/tan` в
радианах) перед занесением в базу — тот же принцип строгости, что и с
теорией вероятности. Заодно нашёл и учёл важный архитектурный нюанс:
"элементарные" примеры вида `sin x = 1/2` дают СЕРИЮ решений (не
единственное число) — такие пошли в карточки теории как иллюстрации, а не
в задачи с числовым ответом; в задачи попали только практические примеры
"отбор корня", где ответ — конкретное целое число. А задачи №13 ЕГЭ
(структура "а) решить б) отобрать корни на отрезке") получают в ответе
СПИСОК значений, а не одно число — для них честно использован уже
существующий формат `DETAILED` (развёрнутый ответ с самопроверкой по
эталону), что точно соответствует реальному формату части C в самом ЕГЭ,
а не является обходным путём.

двух навыков через прямые вызовы API → третий навык разблокировался →
открыл DETAILED-задачу → отправил решение → увидел эталон для
самопроверки с начислением XP.

## Второй предмет: Теория вероятности (первая реальная проверка мультипредметности)

Контент подготовлен на основе реальных материалов преподавателя (три
конспекта — базовые понятия/классическая вероятность, дерево вероятностей,
подборка задач из сборника И.В. Ященко) — не сгенерирован с нуля.
Числовые ответы перепроверены вручную через Python с точными дробями
(`fractions.Fraction`), а не переписаны из PDF на веру — в процессе
проверки нашёл и исправил собственную ошибку в одном из первых пересчётов.

Все 7 запланированных навыков заведены (38 задач): "Основные понятия.
Классическая вероятность", "Несколько испытаний подряд", "Несовместные
события. Сумма вероятностей", "Дерево вероятностей. Цепочки событий",
"Выбор нескольких предметов без возврата", "Рассадка и порядок",
"Условная вероятность. Комбинаторика".

**Важная находка при систематической самопроверке — не только числа, но и
сами условия.** Первый проход (первые 2 навыка) проверялся только на
уровне ЧИСЕЛ — пересчитывал ответы через Python и радовался, что они
сошлись. При наполнении оставшихся навыков стал по инерции реконструировать
некоторые условия по памяти о МЕТОДЕ решения, подбирая правдоподобные числа
под уже известный ответ — вместо того, чтобы каждый раз лезть в исходный
PDF за дословным текстом. Формально число почти всегда получалось верным
(логика метода была правильной), но условие задачи оказывалось не тем, что
реально написано в материалах — а это прямо противоречило указанию "бери
задания прямо отсюда".

Когда прогнал систематическую проверку по всем 39 добавленным задачам
(не выборочно, а по каждой) — нашлось **11 задач с придуманным или
искажённым условием**, включая полностью выдуманную классическую задачу
про диагностику гепатита (её в материалах нет вообще — она из общих
знаний о теореме Байеса, не из файлов пользователя) и задачи про "танк",
которого в материалах тоже нет. Каждую из 11 заменил на дословный текст
из PDF (используя настоящие числа условия, не подогнанные под известный
ответ) — где не нашёл достоверный источник (2 задачи про билеты без
возврата), задачу честно убрал, а не оставил с сомнительным
происхождением. Итог: 38 задач, ноль эпизодов, которые не смог бы
показать в первоисточнике по первому требованию.

**Два реальных архитектурных бага нашлись и исправлены именно благодаря
второй теме** (структура была самодостаточной для одной темы, но не была
по-настоящему протестирована на нескольких):

1. `getAllSkillsFlat()` в `lib/queries.ts` сортировал главы (subtopics)
   только по `order` — а `order` уникален лишь ВНУТРИ одной темы, не
   глобально. У "Треугольников" (Планиметрия) и "Теория вероятности" обе
   `order=1` — SQL не разделял их по темам, и порядок между темами
   получался произвольным (первым в общем списке иногда оказывался навык
   вероятности вместо навыка планиметрии). Исправлено — сортировка теперь
   учитывает пару (порядок темы, порядок главы внутри неё).
2. Страница самого навыка (`app/student/skill/[id]/page.tsx`) считала
   прогресс/блокировку (`getPathStates`) по ПЛОСКОМУ списку навыков сразу
   по ВСЕМ темам — из-за этого первый навык второй темы наследовал
   "заблокированность" от непройденной первой (`getPathStates` трактует
   любой переданный список как одну непрерывную цепочку). Исправлено —
   теперь берутся только навыки ТОЙ темы, куда входит открываемый навык
   (через `getCurriculum()`, а не `getAllSkillsFlat()`).

Оба бага поймал не на глаз, а через прямую пошаговую отладку: сначала через
`getAttribute('href')` подтвердил, что ссылка технически верная, затем
временный `console.log` прямо перед `redirect()` показал точную причину
(`allSkills[0].id` был не тем навыком, что ожидался).
