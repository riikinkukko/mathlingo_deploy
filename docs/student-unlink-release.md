# Выпуск отвязки ученика

1. Сохранить резервную копию схемы и данных. До выпуска проверить миграции `0053_student_unlink`, `0054_verified_parent_links` и `0055_rollback_safe_notifications` и восстановление копии в отдельном PostgreSQL.
2. Проверить количество учеников, у которых `teacher_id` указывает на отсутствующий аккаунт или аккаунт другой роли. Миграция сохраняет эти ссылки без изменений. Список для сверки получает владелец платформы.

   ```sql
   SELECT u.id, u.teacher_id
   FROM users u
   LEFT JOIN users t ON t.id = u.teacher_id
   WHERE u.role = 'STUDENT' AND u.teacher_id IS NOT NULL
     AND (t.id IS NULL OR t.role <> 'TEACHER');
   ```

3. Проверить SMTP, Telegram, URL локальной проверки веба (по умолчанию `http://127.0.0.1:3000/login`), права миграции и наличие места на отдельные сборки. Веб и воркер должны обращаться к одному writable PostgreSQL по прямому соединению или через session pooling. Проверить сохранение backend PID между запросами и ожидание advisory lock на втором соединении в изолированном окружении с такими же параметрами.
4. Workflow передаёт точный SHA. Под `flock` скрипт собирает отдельный каталог и фиксирует намерение переключения на диске. Останавливает старый воркер, затем веб, сохраняет остановленное состояние PM2, применяет миграции и запускает проверяемую пару. Маркер Telegram содержит идентификатор запуска, каталог релиза, PID процесса PM2 и время готовности. Запись появляется после успешного polling и проверки PostgreSQL. Указатель меняется после проверок обоих процессов. Журнал снимается после сохранения новой пары в PM2.
5. При прерывании повторный запуск сначала читает журнал и сверяет указатель с процессами PM2. До фиксации указателя восстанавливается предыдущая безопасная пара. После фиксации повторно проверяется зафиксированная пара, с возвратом на предыдущую при сбое. Скрипт допускает откат на проверенные артефакты этого механизма. При первом выпуске такого артефакта нет. Если переключение не удаётся, веб и воркер остаются остановленными, а оператор повторяет выпуск исправленного SHA. Миграции `0053`–`0055` сохраняются. Представления закрывают неподтверждённые родительские связи и отчёты даже при чтении прежним API. Триггер продолжает блокировать физическое удаление ученика.
6. После успешного переключения проверить веб-отвязку, старое мобильное действие `deleteStudent` и новое `unlinkStudent`, подтверждение родителя и получение контрольного события Telegram. Выпущенная старая мобильная сборка может показывать прежний текст об удалении и привязке родителя. API создаёт ожидающую проверку заявку. После повторной привязки той же пары старый API отвязки попросит обновить приложение.

Журнал, проведённые занятия и оплаты сохраняют исходного репетитора. При повторной привязке старые группы, уроки и оплаты не становятся частью новой связи. `users.teacher_id` остаётся nullable, с прежними правилами ссылочной целостности. Отдельный процесс удаления проверяет запрос владельца аккаунта и выполняет одобренное удаление в отдельной транзакции с `SET LOCAL planimetrika.allow_student_account_delete = 'approved'`.

## Подтверждение самостоятельного доступа

При самостоятельной регистрации ссылка из письма открывает форму нового пароля. Просмотр страницы не расходует ссылку и не даёт права на отвязку. Сохранение нового пароля погашает ссылку, отзывает прежние веб- и мобильные сессии, старые ссылки сброса и привязки Telegram/push. Только следующий успешный вход с новым паролем разрешает отвязку. Старые аккаунты сохраняют вход и используют процедуру передачи через поддержку, в том числе после когда-либо принятого приглашения.

Для существующего аккаунта владелец платформы открывает ученика в админке. Перед выдачей кода он сверяет личность по контакту, происхождение которого подтверждено независимо от репетитора. Для ученика с коротким логином нужно согласовать независимый канал доставки с самим учеником или его законным представителем, не используя канал, доступный репетитору. Для входа по email владелец отдельно подтверждает контроль ученика над зарегистрированным ящиком, поскольку в него будут приходить ссылки сброса. Если это подтвердить нельзя, код не выдаётся и отвязка не разрешается. Отметка в админке фиксирует решение оператора, система сама личность не проверяет.

Код действует 30 минут, привязан к аккаунту и версии связи, сохраняется в БД в виде хеша и используется один раз. Повторная выдача отменяет прежний код. Передавать его нужно напрямую, без пересылки через репетитора. Ученик использует код в веб-профиле, выбирает новый пароль и входит с ним. Старые сессии и ссылки входа теряют силу при смене пароля. Токены, выпущенные до появления версии учётных данных, для аккаунтов с ранее изменённым паролем потребуют один повторный вход. Успешная отвязка сохраняет новые сессии.

## Проверка родительского доступа

Миграция `0054_verified_parent_links` сохраняет исходные записи и аккаунты. Существующие связи, происхождение которых подтвердить по прежней схеме нельзя, закрыты для чтения прогресса, отчётов и материалов до повторной проверки. Запрос репетитора не выдаёт пароль. Владелец платформы независимо проверяет личность родителя и его контроль над зарегистрированным почтовым ящиком, затем согласовывает конкретную связь с учеником или его законным представителем. Подтверждение со слов репетитора недостаточно. Для собственного ученика, включая уже отвязанного по новой схеме, владельцу нужен другой уполномоченный оператор. Если у родителя нельзя подтвердить этот адрес, доступ остаётся ограниченным.

После подтверждения в админке одноразовая ссылка отправляется на проверенный адрес. Родитель задаёт пароль сам. Сервер активирует только указанную связь, отзывает прежние сессии, незавершённые ссылки сброса и привязки Telegram/push. При повторной проверке для ещё одного ученика пароль также меняется, прежние проверенные связи сохраняются. Отвязка репетитора не затрагивает подтверждённые связи.

## Граница доставки уведомлений

Отложенная внешняя доставка несёт идентификатор периода связи. PostgreSQL сериализует передачу поставщику и отвязку на выделенном соединении: доставка берёт разделяемую advisory-блокировку, отвязка берёт исключительную, затем фиксирует короткую транзакцию. Сетевые вызовы выполняются без открытой транзакции. Блокировка удерживается до завершения ограниченного по времени вызова, при обнаружении потери соединения текущая отправка отменяется. Нужны прямое подключение PostgreSQL или пул в режиме session. Перед выпуском нужно сверить этот режим на сервере и обновить веб и воркер Telegram вместе.

Если отвязка зафиксировалась первой, старая доставка не начинается, даже после новой привязки той же пары. Уже переданное внешнему провайдеру сообщение может поступить позднее, в том числе после тайм-аута. Приложение не может его отозвать. Уже записанные внутренние уведомления сохраняются в истории. Внешняя доставка остаётся best effort без гарантии повтора.

Передача учётных данных берёт ту же исключительную advisory-блокировку, что и отправка использует для проверки получателя. Напоминание читает актуальный Telegram-чат под блокировкой. Отложенная доставка отменяется, если пароль получателя сменился после выбора; прежний внешний провайдер всё ещё может доставить сообщения, которые уже принял.

Уведомления репетитору и ответы с данными занятий сверяют адрес Telegram под общей блокировкой с отключением привязки. Автоматические сводки и напоминания под той же блокировкой сверяют настройку доставки.

## Восстановление при старте Timeweb

До первого выпуска владелец устанавливает проверенный `scripts/deploy.sh` как стабильный файл `/usr/local/lib/planimetrika/deploy.sh` (обновлять атомарно вместе с изменениями формата журнала). Установить `scripts/systemd/planimetrika-recovery.service` и поместить `scripts/systemd/nginx-recovery.conf` в drop-in nginx. Если nginx обслуживает другие сайты, использовать отдельный ingress для Планиметрики с той же зависимостью. В unit и `/etc/planimetrika/recovery.env` задать фактического пользователя через `User=`, одинаковые с выпуском `PM2_HOME`, `APP_DIR`, `PATH` с Node/PM2 и локальный URL проверки. Legacy startup unit PM2, вызывающий `resurrect`, необходимо вывести из цепочки старта. Штатный запуск через systemd исполняет `--recover-only`, который читает журнал и указатель, останавливает существующие процессы, собирает согласованное состояние PM2 заново и заменяет сохранённый список. Внешний трафик открывается только после успешной проверки. Если сервис упал, nginx с этой зависимостью не должен открывать трафик для приложения.

Первый запуск без безопасного артефакта повторяет выпуск только по процедуре оператора с закрытым ingress. После появления артефакта проверить статус unit, совпадение каталогов двух процессов с `.releases/current`, готовность нового PID воркера и HTTP. При ошибке смотреть журнал systemd, сохранить журнал выпуска, исправить причину и повторить `--recover-only`. Если оба артефакта недоступны, оставить ingress закрытым до выпуска проверенной версии. `pm2 resurrect` не используется как восстановление прерванного выпуска.

Отключение Telegram линеаризуется с записью по блокировке строки репетитора, а отложенная доставка проверяет актуальную настройку под блокировкой получателя. Сообщение, уже принятое внешним провайдером, может быть доставлено после отзыва.
