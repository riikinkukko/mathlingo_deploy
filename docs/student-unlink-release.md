# Выпуск отвязки ученика

1. Сохранить резервную копию схемы и данных. До выпуска проверить миграцию `0053_student_unlink` и восстановление копии в отдельном PostgreSQL.
2. Проверить количество учеников, у которых `teacher_id` указывает на отсутствующий аккаунт или аккаунт другой роли. Миграция сохраняет эти ссылки без изменений. Список для сверки получает владелец платформы.

   ```sql
   SELECT u.id, u.teacher_id
   FROM users u
   LEFT JOIN users t ON t.id = u.teacher_id
   WHERE u.role = 'STUDENT' AND u.teacher_id IS NOT NULL
     AND (t.id IS NULL OR t.role <> 'TEACHER');
   ```

3. Обновить сервер и Telegram-воркер до выпуска мобильной сборки. Проверить веб-отвязку, старое мобильное действие `deleteStudent` и новое `unlinkStudent`. Выпущенная старая сборка по-прежнему показывает текст об удалении. Сервер выполнит безопасную отвязку, если у пары ещё не было отвязки по новой схеме и ученик подтвердил самостоятельный вход. После повторной привязки той же пары API попросит обновить приложение.
4. Для отката приложения оставить миграцию и ограничение удаления в базе. Старое действие физического удаления получит SQLSTATE `42501`, включая окно между миграцией и перезапуском приложения. Если потребуется откат схемы из резервной копии, сначала закрыть старый путь удаления на уровне приложения и вернуть защиту базы до открытия доступа.

Журнал, проведённые занятия и оплаты сохраняют исходного репетитора. При повторной привязке старые группы, уроки и оплаты не становятся частью новой связи. `users.teacher_id` остаётся nullable, с прежними правилами ссылочной целостности. Отдельный процесс удаления проверяет запрос владельца аккаунта и выполняет одобренное удаление в отдельной транзакции с `SET LOCAL planimetrika.allow_student_account_delete = 'approved'`.

## Подтверждение самостоятельного доступа

При самостоятельной регистрации ссылка из письма открывает форму нового пароля. Просмотр страницы не расходует ссылку и не даёт права на отвязку. Сохранение нового пароля погашает ссылку, отзывает прежние веб- и мобильные сессии, старые ссылки сброса и привязки Telegram/push. Только следующий успешный вход с новым паролем разрешает отвязку. Старые аккаунты сохраняют вход и используют процедуру передачи через поддержку, в том числе после когда-либо принятого приглашения.

Для существующего аккаунта владелец платформы открывает ученика в админке. Перед выдачей кода он сверяет личность по контакту, происхождение которого подтверждено независимо от репетитора. Для ученика с коротким логином нужно согласовать независимый канал доставки с самим учеником или его законным представителем, не используя канал, доступный репетитору. Для входа по email владелец отдельно подтверждает контроль ученика над зарегистрированным ящиком, поскольку в него будут приходить ссылки сброса. Если это подтвердить нельзя, код не выдаётся и отвязка не разрешается. Отметка в админке фиксирует решение оператора, система сама личность не проверяет.

Код действует 30 минут, привязан к аккаунту и версии связи, сохраняется в БД в виде хеша и используется один раз. Повторная выдача отменяет прежний код. Передавать его нужно напрямую, без пересылки через репетитора. Ученик использует код в веб-профиле, выбирает новый пароль и входит с ним. Старые сессии и ссылки входа теряют силу при смене пароля. Токены, выпущенные до появления версии учётных данных, для аккаунтов с ранее изменённым паролем потребуют один повторный вход. Успешная отвязка сохраняет новые сессии.

## Граница доставки уведомлений

Отложенная внешняя доставка несёт идентификатор периода связи. PostgreSQL сериализует передачу поставщику и отвязку на выделенном соединении: доставка берёт разделяемую advisory-блокировку, отвязка берёт исключительную, затем фиксирует короткую транзакцию. Сетевые вызовы выполняются без открытой транзакции. Блокировка удерживается до завершения ограниченного по времени вызова, при обнаружении потери соединения текущая отправка отменяется. Нужны прямое подключение PostgreSQL или пул в режиме session. Перед выпуском нужно сверить этот режим на сервере и обновить веб и воркер Telegram вместе.

Если отвязка зафиксировалась первой, старая доставка не начинается, даже после новой привязки той же пары. Уже переданное внешнему провайдеру сообщение может поступить позднее, в том числе после тайм-аута. Приложение не может его отозвать. Уже записанные внутренние уведомления сохраняются в истории. Внешняя доставка остаётся best effort без гарантии повтора.
